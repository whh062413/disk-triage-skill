# 案例复盘：aigo U351（58.6 GB FAT32）卷头被覆盖

这是本技能方法的来源案例。记录完整的证据链、每一个判断的依据、以及最终结果——
包括**没救回来的部分**。

---

## 1. 现象

- U 盘插上后 Windows 提示"需要格式化"
- 资源管理器打不开，`dir E:` 返回
  `The volume does not contain a recognized file system`
- `Get-Volume`：`FileSystemType = Unknown`、`Size = 0`、`HealthStatus = Healthy`
- `Get-Disk`：设备 Online / Healthy / 非只读；`Get-PnpDevice`：状态 OK
- 分区信息正常：偏移 32,768 字节、大小 62,914,347,008 字节、MBR 类型 `0x0B`（FAT32 标志）

**第一层结论**：设备在线、分区表可读、介质能读——问题在**文件系统层**，不是掉盘也不是掉驱动。

---

## 2. 只读取证

用卷句柄 `\\.\E:` 只读打开（**非管理员即可**），逐层读取：

| 位置 | 实际内容 | 判定 |
|---|---|---|
| LBA0（引导记录槽位） | `01 FE 0C 40 02 EE 18 00 …`，无 `55AA`、无 BPB | **被外来数据覆盖** |
| LBA1（FSInfo） | `RRaA` + `rrAa` + `AA550000` 三签名齐全 | **完好** |
| LBA2–LBA31 | 与 LBA0 同类的外来结构化数据 | 被覆盖 |
| LBA6（备份引导） | 非引导记录 | 被覆盖 |
| LBA7（备份 FSInfo） | 签名错误 | 被覆盖 |
| LBA32–LBA53 | 全零 | 正常 |
| LBA54 起 | `F8 FF FF 0F FF FF FF 0F` | **FAT1 完好** |

**关键不对称**：整段头 16 KB 里，唯独 LBA1 完好。这直接排除了"连续块被整段覆写"的解释，
也解释了为什么"只要把引导记录补回去"就可能可行。

**为什么 Windows 只提供格式化**：没有合法 BPB 就无法确定簇大小、FAT 位置、根目录位置，
内核无法挂载，于是只剩"格式化"这一个动作。

---

## 3. 几何反推

按 `references/fat32-geometry.md` 的公式，从 FAT1/FAT2 的偏移差反推出全部参数
（512 字节/扇区、64 扇区/簇、保留 54 扇区、FAT 各 14,997 扇区、总扇区 122,879,584、
数据区起点 15,384,576、隐藏扇区 64）。

**交叉验证**：推导出的数据区起点 15,384,576 处读出的第一条目录项正是 `LOST    DIR`，
偏移 +64 是 `ANDROID    ` —— 与推导位置逐字节吻合。

同时发现：**FAT1 与 FAT2 有 85 个扇区不一致**，分布对应盘上约 46–62 GB 位置——
这是"写入未完成即断电/拔盘"的痕迹，且预示损坏集中在特定的文件区域。

---

## 4. 写入动作（最小化）

写回**仅 3 个扇区、共 1,536 字节**：

| 扇区 | 内容 |
|---|---|
| LBA0 | 重建的引导记录（BPB） |
| LBA6 | 同一份（备份引导记录） |
| LBA7 | 复制自完好的 LBA1（备份 FSInfo） |

写前闸门：现场复核（FSInfo 三签名 / 两个 FAT 的介质描述符 / 根目录条目）+ 备份原始 4 个扇区；
写后：回读校验三项全部通过。

**结果**：卷被识别为 `FAT32`、`AllocationUnitSize = 32768`（正是重建时写入的 32KB 簇），
根目录四项与修复前的裸扇区解析结果**完全一致**，`Android\data` 下 55 个条目录目吻合。

---

## 5. 拷贝与抢救结果

| 项目 | 数量 |
|---|---|
| 盘上文件总数 | 7,080 |
| 常规拷贝成功 | 7,061（57.89 GB，14 分 28 秒，平均 75 MB/s） |
| 拷贝失败 | 19（576.78 MB） |
| 结构校验又抓出的"假成功"文件 | 2 |
| **最终可用** | **7,075** |
| **无法恢复** | **5** |

抢救用到的策略（按顺序）：FAT2 链 → 连续簇 → 截断到 EOI → 保留有效片段 → 指纹雕刻。

### 5.1 成功的部分

- 10 张微信导出图（`mmexport*`）通过**连续簇**恢复，JPEG 结构校验显示 3072×4096 等分辨率、
  `SOS` 与 `EOI` 齐全
- 2 张动态照片通过 **FAT2 链**恢复（其中一张是常规拷贝"成功"但头部在 33,831 字节处断裂的
  ——**逐字节校验抓不到它**）
- 3 个视频通过连续簇恢复，MP4 盒子链**精确走到文件末尾**且 `moov` 完整
- 1 张照片的头部与图像本体完好，取出了内含完整 JPEG 的 1.25 MB 片段

### 5.2 失败的部分

5 个文件的数据簇已被覆盖：目录项记录的首簇指向的数据不是对应文件；
在首簇前后各 2 GB 范围内做"精确文件大小 + JPEG 结尾标记"的指纹扫描均未命中。

**处置**：逐条列清单（文件名、大小、日期、判断依据、找回建议），并说明"这 5 个是连拍序列"，
用户核对后确认实质损失为零。**没有把它们说成"已恢复"。**

---

## 6. 这个案例教出来的东西

1. **"卷打不开"与"数据没了"是两件事**——本例 99.93% 的文件从未损坏
2. **只读取证不需要管理员**（卷句柄），这决定了可以先把结论做扎实再动盘
3. **头 16 KB 里 LBA1 独活**这种不对称，是判断"整段覆写"还是"局部损坏"的关键证据
4. **结构校验必须独立于字节校验**——两个"拷贝成功但内容是坏的"文件只有结构校验能抓
5. **验证脚本自身也要有阳性对照**——本次扫描器的一个对齐 bug 差点把可救的文件判死
6. **不承诺恢复率**：5 个没救回来就是没救回来，写进清单，给出替代找回路径
