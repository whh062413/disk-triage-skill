# 陷阱清单

> 12 条全部来自一次真实事故（FAT32 卷头被覆盖）的复盘。其中 4 条曾**直接把结论带偏**，
> 造成过误判：把好的文件判成损坏、把脚本 bug 判成盘坏、把正常现象判成数据丢失。

每条格式：**现象 → 原因 → 正确做法**。

---

## 1. 卷句柄读取必须 512 字节对齐

**现象**：读取 `\\.\E:` 时抛 `The parameter is incorrect`，或更误导人的
`Handle does not support synchronous operations. The parameters to the FileStream constructor may need to be changed...`

**原因**：后一个错误信息会让人以为是异步 I/O / FileStream 构造参数的问题，实际几乎总是
**偏移不是 512 的整数倍**（或读取越过了设备末尾）。卷设备对象只接受扇区对齐访问。

**正确做法**：需要读非对齐位置时，把偏移向下对齐到扇区、整扇区读入、再切片：

```powershell
[RawVol]::ReadAny($vol, $offset, $len)   # lib 里已封装
```

**代价示范**：一次"按文件大小匹配 JPEG 结尾标记"的全盘指纹扫描，因为结尾标记的探测偏移
非对齐，导致每个候选都被静默拒绝，输出"全部搜不到"——把 6 张本可进一步分析的照片
误判为彻底丢失。

---

## 2. 文件尾部的"不满簇"读取

**现象**：每个被抢救的文件都比声明大小少最后一块（通常是几百字节到 30 KB）。

**原因**：`ceil(size/cluster)` 的最后一簇里只需要 `size % cluster` 字节，
按这个长度去读设备 → 长度不是 512 的整数倍 → 与第 1 条同源的失败。

**正确做法**：**读满一整簇，只写需要的字节**：

```csharp
byte[] cb = img.ReadCluster(c);            // 整簇，对齐
int take = (int)Math.Min(ClusterSize, remain);
o.Write(cb, 0, take);                       // 只写需要的
```

修掉之前，19 个抢救文件**全部**缺最后一簇（8 张 JPEG 因此判定"无 EOI"）；修掉之后同一批
文件 10 张直接通过完整校验。

---

## 3. 并发访问同一设备会伪造损坏

**现象**：镜像与源盘在零星扇区不一致；某 1 MB 块里出现"别处 LBA 的内容"；
文件头在第二个簇处断掉。

**原因**：廉价 USB 桥在多个句柄/线程同时读同一设备时，会出现读超时与错位返回。
更隐蔽的是：采集器在重试耗尽后**按零填充**，于是镜像里出现"源盘有数据、镜像是零"的扇区——
看起来像介质损坏，实际是采集过程自己造成的。

**正确做法**：
- 镜像/校验**严格串行**，期间不对该设备做任何其它读取（包括进度探测之外的并发测试）。
- 采集器必须**记录**零填充的 LBA，而不是默默填零。
- 判据：**两次独立采集同一区域，哈希一致 = 源数据可复现**；若两次采集一致而与镜像不符，
  问题在镜像侧（重跑镜像），不在介质侧。

---

## 4. 逐字节校验抓不到"链指错"型损坏

**现象**：文件拷贝全程无报错、大小正确、与源盘逐字节一致，但内容不是该文件。

**原因**：目录项的首簇或 FAT 链指向了错误的簇。源和副本读的是**同一份错误数据**，
所以任何哈希比对都会通过。

**正确做法**：做**结构校验**，而不是字节校验：

| 类型 | 判据 |
|---|---|
| JPEG | `FFD8` 开头 + 分段结构走到 `SOS` + 头部之后存在 `FFD9` |
| PNG | `89504E47` 开头 + 尾部存在 `IEND` |
| MP4 | 盒子链从 `ftyp` 走到文件末尾 + 存在 `moov` |

本次正是靠结构校验抓出 2 个"拷贝成功但内容是坏的"文件（其中一个在拷贝日志里完全正常）。

---

## 5. 手机媒体的尾部附加数据是正常的

**现象**：大量照片最后两个字节不是 `FFD9`；判定为"尾部缺失"。

**原因**：手机相机的产物普遍带 trailer：
- 动态照片（MVIMG / Motion Photo）：JPEG 后追加一段视频；
- 深度信息、相机固件信息：本次案例中见过 `ctrace`、`DepthP`、`VshapEn` 这类 ASCII 标记。

**正确做法**：结尾标记只在**头部之后全文搜索**，不要只看文件末尾；不要以"EOF 是否等于
`FFD9`"作为判据。同理 MP4 允许 `mdat` 之后跟一段非 ISO 盒子的附加数据
（本次 57 个视频的 trailer 是 `modelELSNX9buildVersion12.0.0.37`，全部正常）。

## 6. FAT1 不一定是正确的那一份

**现象**：按 FAT1 走链，文件链长与大小不符；换 FAT2 就对了；或两者都错。

**原因**：FAT 镜像（FAT1/FAT2）在**写入被中断**后会不同步。这次案例中两张表有 85 个扇区
不一致，且损坏方向不同——有的文件 FAT1 对、FAT2 错，有的反过来。

**正确做法**：两条链都走，用**物理约束仲裁**：

```
need = ceil(size / clusterSize)
valid = (无越界/空闲/自环错误) 且 (链长 == need)
```

只信"链自洽"的那一份；两份都自洽时优先 FAT1（Windows 的默认行为）；
两份都不自洽时进入抢救流程（连续簇假设 + 结构校验 + 指纹扫描）。

---

## 7. 链长"超过"需要长度不等于坏

**现象**：链长 199 而 `need` 只有 153，被判定为异常。

**原因**：多出来的簇只是链尾冗余（可能与别的文件交叉链接）。文件本身前 `need` 个簇的
字节仍然可用。

**正确做法**：链更长时**照常读**，但必须做结构校验——因为交叉链接意味着内容可能被
别的文件覆盖。本次案例里就有一个这样的文件：链长正常但内容是错的。

---

## 8. 用"是否需要管理员"来区分访问层级

**现象**：以为读裸设备一定需要管理员，于是放弃诊断。

**原因**：**卷句柄**（`\\.\E:`）对未挂载/无法识别的卷，普通用户即可只读打开；
**物理盘句柄**（`\\.\PhysicalDrive1`）才必须管理员。

**正确做法**：诊断与镜像阶段优先用卷句柄，可以完全在非提权会话里完成；
只有写回（`WriteSectors`）与整盘镜像才需要管理员。这决定了技能的分层设计：
**只读部分零权限门槛，写入部分强制提权 + 多重闸门**。

---

## 9. 写盘的物理风险区 = LBA0 所在的 NAND 擦除块

**现象**：以为"只写 512 字节"就没有风险。

**原因**：NAND 以擦除块为单位改写。LBA0 所在的擦除块通常也覆盖卷的保留区，
**并可能覆盖 FAT1 的起始部分**（保留区 + FAT1 起始常在头几 MB 内）。

**正确做法**：写回之前先取得覆盖风险区的**头部保险镜像**（本次取 256 MB，
远大于典型擦除块），并且要求两次采集哈希一致。只写 3 个扇区（LBA0 / 备份引导 / 备份 FSInfo），
绝不触碰 FAT 与目录。

---

## 10. 不要相信 GUI 工具的"自动修复"

**现象**：格式化、`chkdsk /f`、"扫描并修复驱动器"看起来是省事的出路。

**原因**：这三者都会**改写 FAT 与目录**。当损坏只是引导记录时，它们会把"可无损修复"
变成"需要按簇雕刻"。

**正确做法**：任何写入之前先镜像；修复只重建确实损坏的扇区；`chkdsk` 只在
**数据已导出并校验通过之后**、且明确接受其改动时执行。

---

## 11. 非 ASCII 内容写进 .ps1 会被破坏

**现象**：脚本里带中文时，PowerShell 解析报
`Missing closing '}'`、`常量中有换行符`，或 Add-Type 编译报 `无效的表达式项`、
字符串被截断成 `?`。

**原因**：脚本文件被以非 UTF-8 编码读取，中文多字节序列被破坏，恰好落在字符串
边界上时就把引号/括号结构吃掉了。

**正确做法**：
- **脚本保持纯 ASCII**（消息用英文），可读的中文说明放 `.md`；
- 必须包含非 ASCII 时，写完文件后**补 UTF-8 BOM**再执行：

```powershell
$t = [System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)
[System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding($true)))
```

## 12. PowerShell 十六进制字面量的符号陷阱

**现象**：校验门永远失败，但打印出来的值完全正确。

**原因**：`0xAA550000` 在 PowerShell 里被解析为**负数 Int32**（-1437270016），
而 `[BitConverter]::ToUInt32()` 返回正数，两者 `-eq` 永远为假。
一个"FSInfo 三签名校验"因此误报，差点让写回流程在管理员面前中止。

**正确做法**：比较格式化后的十六进制字符串，而不是数字：

```powershell
if (('{0:X8}' -f [BitConverter]::ToUInt32($s,0)) -ne '41615252') { ... }
```

同类问题：`Add-Type` 用的 C# 编译器版本较旧——不支持 `out var`、
字符串插值、表达式体成员；且**警告可能被当作错误**（未使用的变量会导致编译失败）。
保持 C# 5 语法、不留未使用局部变量。

## 附：一条流程纪律

**"找不到"和"不存在"是两回事。** 指纹扫描报告 "not found" 之前，先用一个**已知完好**的
同类文件做一次阳性对照——确认扫描器本身能命中（delta 0）。本次正是靠这个对照
发现扫描器有 bug，否则会把 6 张可进一步分析的照片直接判死。
